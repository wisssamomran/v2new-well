# خطة تطوير خادم Express وواجهات API وقواعد العمل والصلاحيات لمنصة «دلنّي»

## ملخص الخطة والهدف الرئيسي
بناء خادم Express متكامل ومحرك خدمات خلفية (Backend Services & RESTful APIs) مع حوكمة صارمة لقواعد العمل (Business Rules) ومصفوفة الأدوار العشرة (10-Role RBAC Middleware)، وتوفير قاعدة بيانات محلية سريعة ومستقرة، مع تشفير وحماية الخصوصية الجغرافية، وتوثيق سجل تدقيق مركزي (Audit Log) غير قابل للتلاعب.

---

## مراجعة المستخدم والقرارات الحاسمة (User Review & Critical Decisions)

> [!IMPORTANT]
> بناءً على إجاباتك المؤكدة في مرحلة التوضيح، تم اعتماد القرارات التالية كأساس معماري:
> 1. **بنية الخادم:** خادم Node.js / Express متكامل مدمج مع وسائط Vite في التطوير (`server.ts`)، مع قاعدة بيانات محلية سريعة (Persistent Local JSON/SQLite Engine) مع معالجة غير متزامنة وآمنة.
> 2. **آلية فحص الصلاحيات:** وسيط سيرفر صارم (`rbacMiddleware`) يتحقق من رمز التوثيق (`Authorization: Bearer <token>` أو ترويسة الجلسة المعرفة للدور)، مع فحص مطابقة الدور والمورد المستهدف (Resource-level RBAC).
> 3. **قواعد العمل الإلزامية في الخادم:**
>    - **حظر الاعتماد الذاتي:** منع المعلن أو المنشأة برمجياً من نقل إعلانه مباشرة إلى «منشور»؛ تمر جميع الإعلانات عبر طابور المراجعة فقط.
>    - **حماية الخصوصية الجغرافية:** حفظ الإحداثيات الحقيقية الدقيقة للمعلن والإدارة فقط، وإرجاع إحداثيات مشوشة بنصف قطر أمان عشوائي (Fuzzed Geolocation) للزوار والباحثين.
>    - **التحقق من رقم الهاتف اليمني:** التحقق الإجباري من صحة صيغة الهاتف اليمني (يمن موبايل 77/78، سبأفون 71، يو 73، واي 70، أو الهاتف الثابت) قبل قبول أي إعلان.
>    - **سجل تدقيق أوتوماتيكي متواصل:** تسجيل كل عملية (إنشاء، تعديل، تغيير حالة، دخول، فحص مستند) في جدول التدقيق بالخادم.

## 1. النظرة العامة والمفهوم الأساسي (Overview & Core Concept)

- **ما تقدمه المنظومة:** تحويل المنصة من مجرد واجهة تفاعلية إلى تطبيق متكامل (Full-Stack Architecture) يمتلك خادم API مستقل على المسارات `/api/*` يدير دورة حياة العقارات، والمنشآت، والتوثيق، والبلاغات، والتذاكر، وسجلات التدقيق بموثوقية عالية.
- **الفئة المستهدفة:** جميع أطراف السوق العقاري اليمني (الباحثون، الملاك، المكاتب العقارية، ومشرفو المنصة والقانونيون).
- **القيمة المضافة:** ضمان عدم إمكانية الالتفاف على القواعد من خلال المتصفح أو التعديل على الحالة محلياً، حيث يصبح الخادم هو المرجع التشغيلي النهائي (Single Source of Truth).

---

## 2. الواجهات التشغيلية وتجربة الاستخدام (User Experience & API Integration)

- **انتقال سلس بدون انقطاع (Seamless Client-Server Sync):**
  - تحديث `AppContext` ليعمل كـ API Client يستعلم ويحدث البيانات عبر `/api/*` مع دعم التخزين المؤقت والتخزين الاحتياطي (Optimistic Updates + Fallback).
  - إظهار مؤشرات تحميل دقيقة وتنبيهات خطأ (Error Toasts) متوافقة مع رموز حالة HTTP الرسمية (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity).
- **تجربة محاكي الأدوار في الواجهة:**
  - عند تغيير الدور من شريط محاكي الأدوار (`RoleSwitcher`)، يرسل العميل ترويسة التوثيق المتوافقة مع الدور المختار إلى الخادم، مما يتيح اختبار استجابة الخادم لكل دور فورياً.

---

## 3. القرارات المعمارية الرئيسية (Key Product Decisions & Trade-Offs)

- **القرار 1: استخدام Express مع Vite Middlewares داخل ملف `server.ts`**
  - *النهج المختار:* تشغيل خادم Express على المنفذ 3000 ودمج `vite.middlewares` في وضع التطوير، مما يمنح استجابة فائقة السرعة للمسارات الثابتة مع توفير واجهات RESTful API كاملة بدون تعارض منافذ.
  - *السبب:* الامتثال الصارم لبيئة تشغيل AI Studio (المنفذ 3000)، وسرعة الإقلاع والأداء العالي.
- **القرار 2: عزل وتجريد قاعدة البيانات المحلية السريعة (DB Abstraction Layer)**
  - *النهج المختار:* إنشاء وحدة تخزين محلية في `src/server/db.ts` تضمن الكتابة الآمنة والمتسلسلة للملفات على القرص مع فهرسة في الذاكرة لسرعة الاستعلام، وتوفير نقاط استعادة (Seed Data).
  - *السبب:* استقلالية التطبيق وسرعة التشغيل المحلي دون الحاجة لتهيئة خدمات خارجية معقدة.

### واجهات الـ API التفصيلية (REST Endpoints Specification):

| المسار (Endpoint) | الطريقة (Method) | الدور المصرح له | الوظيفة وقواعد العمل المطبقة |
|---|---|---|---|
| `/api/auth/me` | GET | للجميع | إرجاع بيانات المستخدم الحالي وصلاحياته المعتمدة |
| `/api/auth/switch-role` | POST | الجميع (محاكي) | تبديل جلسة الاختبار لأي دور من الأدوار الـ 10 |
| `/api/listings` | GET | للجميع | جلب الإعلانات المنشورة فقط مع إحداثيات تقريبية (Fuzzed Lat/Lng) للزوار |
| `/api/listings/my-ads` | GET | المعلنون/المنشآت | جلب إعلانات المستخدم الخاصة بجميع حالاتها |
| `/api/listings` | POST | معلن / منشأة / وكيل | إنشاء إعلان جديد، التحقق من الهاتف، وتعيين الحالة تلقائياً إلى `under_review` |
| `/api/listings/:id` | PUT | صاحب الإعلان / الإدارة | تعديل بيانات الإعلان وحفظ التعديلات مع نقل الحالة إلى المراجعة |
| `/api/listings/:id/status` | PATCH | مشرف / إدارة | تغيير حالة الإعلان (`published`, `needs_changes`, `rejected`, `suspended`) مع تدوين السبب |
| `/api/moderation/queue` | GET | مراجع / إدارة | جلب قائمة الإعلانات المنتظرة للمراجعة |
| `/api/verifications` | GET / POST / PATCH | مسؤول التحقق / إدارة | استعراض وفحص طلبات التوثيق ومنح الشارات |
| `/api/organizations` | GET / POST / PUT | مدير المنشأة / إدارة | إدارة ملف المنشأة وفريق الوكلاء |
| `/api/reports` | GET / POST / PATCH | الجميع (إرسال) / مسؤول البلاغات (معالجة) | إدارة الشكاوى والنزاعات |
| `/api/support/tickets` | GET / POST / PATCH | باحث، معلن (إرسال) / الدعم (رد) | متابعة تذاكر الدعم والردود |
| `/api/audit-logs` | GET | مدير النظام فقط (`system_admin`) | جلب سجل التدقيق الشامل وتصفيته حسب التاريخ والمستخدم |

## 5. خطة التنفيذ المتسلسلة (Step-by-Step Execution Plan)

1. **الخطوة 1: بناء طبقة قاعدة البيانات المحلية والخادم الأساسي (`server.ts`)**
   - كتابة `server.ts` وتجهيز محرك التخزين المحلي الآمن مع البيانات الأولية المتكاملة لليمن.
   - تهيئة تشغيل Express مع Vite middlewares في وضع التطوير وتعديل سكربت `dev` في `package.json`.
2. **الخطوة 2: بناء وسيط التحقق من الصلاحيات وقواعد العمل (RBAC Middleware & Validators)**
   - برمجة وسيط التحقق من هوية وأدوار المستخدمين العشرة وحماية المسارات.
   - تطبيق دالة تشويش الإحداثيات لحماية الخصوصية الجغرافية.
   - تطبيق دالة فحص أرقام الهواتف اليمنية الصالحة.
   - برمجة مسجل التدقيق الأوتوماتيكي المركزي.
3. **الخطوة 3: برمجة مسارات الـ API بالكامل**
   - برمجة مسارات العقارات والمراجعة والتحقق والمنشآت والبلاغات والدعم وسجل التدقيق.
4. **الخطوة 4: ربط واجهة العميل (`AppContext.tsx`) بخادم الـ API**
   - تحديث دوال العميل لاستدعاء الـ API مع الاحتفاظ بتجربة مستخدم سريعة وفورية واستقبال التنبيهات.
5. **الخطوة 5: التحقق والاختبار الشامل والتجميع**
   - فحص صحة تشغيل السيرفر وعمل الـ API، والتحقق عبر `lint_applet` و `compile_applet`.
